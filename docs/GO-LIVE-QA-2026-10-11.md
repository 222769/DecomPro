# DecomPro scenario audit — 11 October 2026

Audited application revision: `bc54de8` (isolated synthetic test workspace).
Purpose: identify failures before decommissioning work on 12 October 2026.

**Five confirmed issues remain open. The normal workflow passes, but this audit does not establish that the application is bug-free or ready for unrestricted rollout.** No application fixes or Firestore rule changes were made during this audit. Synthetic data remained in isolated browser contexts; nothing was inserted into the live team database.

## Confirmed bugs

### 1. High: local tabs silently overwrite each other's saved changes

Reproduction:
1. Open the same test workspace in two tabs before editing.
2. In tab A, edit the sixth fixture item's model from `N/A` to `AUDIT FIRST TAB`, and save.
3. In tab B, edit the seventh item's model to `AUDIT SECOND TAB`, and save.
4. Inspect persisted data or reload.

Actual: tab B's change remains, but tab A's saved change has reverted to `N/A`. There is no conflict warning. Reproduced in both the development app and production build.

Cause: tabs retain independent in-memory copies, and local mutations replace the entire workspace in localStorage. The storage-event handler only handles the shared-workspace lock flag; it does not detect workspace revisions. The editor's conflict check compares against its own stale in-memory data.

Impact: previously saved local changes can be lost. This applies to the local persistence mechanism, not a demonstrated bypass of Firestore's server revision checks.

Tomorrow's workaround: use one active editing tab per browser profile. Do not edit a local register in parallel tabs. Use the shared Firebase workspace for collaboration across devices and back up regularly.

Required fix: protect all local mutations with a cross-tab revision/locking strategy, detect stale writes, and preserve unfinished drafts when reconciling updates.

### 2. Medium: delayed shared saves leave a stale collection draft

Reproduction:
1. In an isolated browser, use the synthetic fixtures with a simulated Firebase adapter whose write confirmation is delayed.
2. Resume TEST Current collection and capture a complete item.
3. Click Save, switch to TEST Previous collection while the request is pending, then release confirmation.
4. Resume TEST Current collection.

Actual: the register contains exactly one saved item, but the old collection restores the same complete draft at step 5, showing Save again. The duplicate-serial guard blocks another save for this serial. No duplicate record was demonstrated.

Cause: switching records a checkpoint before confirmation; successful save updates the active draft but leaves that checkpoint unchanged.

Impact: misleading save state and wasted time checking whether equipment was recorded. This was tested with simulated shared transport, not the live Firebase project.

Tomorrow's workaround: wait for save confirmation before switching or pausing collections. If a saved item returns as a draft, check the register and clear that draft.

Required fix: reconcile the original collection checkpoint after confirmation, preserving any newer edits.

### 3. Medium: toggling Voice discards an unsubmitted scan

Reproduction: type `AUDIT-NOT-ENTERED` into the serial input, do not press Enter, then toggle Voice.

Actual: input becomes empty and persisted draft remains `{}`. Reproduced in development and production builds.

Cause: Voice triggers a full render without capturing the current input value.

Impact: a typed or scanner-supplied value without its Enter terminator must be entered again. Accepted scans and saved records were not lost in this scenario.

Tomorrow's workaround: press Enter/Capture value before toggling Voice or other controls that redraw the station.

Required fix: preserve unsubmitted field input across renders separately from accepted scan progress.

### 4. Low, test workspace only: reset leaves a deleted trolley selected

Reproduction: open one test trolley's inventory using its barcode route (`#trolley/<id>`), then Settings → Reset synthetic data.

Actual: storage contains 96 fresh items, but the register says `Showing 0 of 0 items` and `Trolley not found in this workspace`. The old trolley UUID remains selected although reset generated new UUIDs. Reproduced in development and production builds.

Workaround: click Show all inventory. Required fix: clear the trolley route and related view state when resetting.

### 5. Low, test workspace only: reset retains a restrictive search

Reproduction: search the register for `AUDIT-DOES-NOT-EXIST`, then reset synthetic data.

Actual: the refreshed register says `Showing 0 of 72 items`; all 96 items remain stored. The search stays active. Reproduced in development and production builds.

Workaround: clear the search. Required fix: reset search, selections, and review filters consistently when replacing test data.

## Limits and collection-day checks

The execution environment cannot reach the public site through its HTTP proxy, and available credentials cannot authenticate to the live Firebase project. These results validate local source/build behavior and emulator rules; they do not certify the currently deployed site, production permissions, or cross-device live synchronization. The phone test uses Chromium at phone dimensions, not physical iPhone Safari or the actual barcode scanner. Physical print readability, audio quality, scanner terminators, and network reliability remain unverified.
