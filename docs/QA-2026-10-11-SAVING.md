# Save and navigation testing — 11 October 2026

## Findings and fixes

1. **Newer edits could be discarded during Firebase confirmation.** A delayed save was started, then the technician went back and changed the asset number. The old save cleared the edited draft on completion. Saving now sends a snapshot of the reviewed values and only clears the draft if its values and scan position have stayed unchanged. Newer edits and batch defaults stay in place; the saved record keeps the originally submitted values. Confirmed saves are distinguished from subsequent screen-update failures so users are not told to submit an already saved record again.
2. **Scan length was not checked before persistence.** A 1,001-character serial advanced the scan and was stored, despite shared Firestore writes limiting field text to 1,000 characters. Capture now rejects oversized values before changing stored progress. Saved equipment is validated before writing. Existing local records keep their original read-validation behavior and are not truncated.
3. **The phone Scan station navigation link was hidden.** The older responsive style hid that link. It is now visible, and repeated navigation between Overview, Scan station and Collection register preserves an unfinished scan.

## Adversarial scenarios

- Backwards and forwards through asset and model fields, including invalid asset correction and lowercase normalization.
- Leading-zero barcodes, Unicode/text symbols, multiple serials and repeated N/A serials.
- Repeated Save clicks and duplicate-submission prevention while a write is pending.
- Delayed confirmations, rejected server writes and explicit retry.
- Workspace locking during a pending save, with unfinished data retained.
- Editing scan values and batch manufacturer during confirmation; newer work is preserved.
- Clearing a required disposal date, refreshing and then saving a valid leap-day date.
- Oversized scan input rejected without storing malformed progress.
- Phone navigation repeated three times with an unfinished serial.

Earlier regression coverage also exercises missing fields, unchecked recognition suggestions, duplicates, full/blocked browser storage, save-preparation exceptions, backups, imports, PDFs, trolley locks, collection sessions, revoked membership and cross-team access.

## Scope and limits

Browser tests use isolated browser storage and controlled database adapters for network failures; database and authentication authorization are separately tested against Firebase emulators. Production checks run the actual built assets locally. Test records were not inserted into the college's live register. Live website access is blocked by this execution environment's network proxy, so these results do not verify live Firebase project configuration or the exact version currently served by GitHub Pages. No Firestore rule changes are needed for these fixes.

No finite test phase can prove that every possible bug is eliminated. There are no remaining reproduced failures in the scenarios above. A real scanner/device acceptance check on the deployed site remains useful, particularly for scanner timing, browser speech, and real Firebase connectivity.
